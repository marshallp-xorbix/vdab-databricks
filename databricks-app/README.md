# VDAB Databricks App

This directory is the source package for the standalone workspace App. The release artifact is generated at `.build/`; deploy only that directory. The repository-root `package.json` remains unrelated tooling metadata. Generated child apps remain Python/Streamlit.

## Local build and smoke run

Requirements: Node.js 22.16 or later and npm. The existing React client dependencies are installed from its committed lockfile; the Node server dependencies are installed from this directory's lockfile.

```powershell
cd databricks-app
npm run install:all
npm run build
npm run smoke
$env:VDAB_AUTH_MODE = "local-test"
$env:VDAB_LOCAL_USER_ID = "local-editor"
$env:NODE_ENV = "development"
npm run start:packaged
```

The build runs strict server type checking, Node tests, the existing client build in standalone mode, and creates a self-contained `.build/` deployment directory. The committed `runtime/package.json` and `runtime/package-lock.json` pin the production runtime dependency graph; packaging copies them unchanged and does not resolve packages or contact the registry. `start:packaged` runs the packaged server with `.build/` as its working directory so it serves the generated React assets. Open `http://localhost:8000/`; the local adapter returns an explicitly marked empty app list and never contacts Databricks. `GET /api/health/live` is unauthenticated. Local test identity cannot run with `NODE_ENV=production`.

The packaged smoke run verifies the stateless component catalog returns all 33 definitions, the four current-workspace binding schemas, and all eight story types. It also saves and previews TextInput, Button, Checkbox, Toggle, Dropdown, DatePicker, TimePicker, Slider, Label, ordered Expander/Columns/Rows/Tabs children, a Form with ordered TextInput and Checkbox controls, a Modal with a positioned non-dismissible dialog, FileUpload, Unity Catalog DataWindow, Unity Catalog Delta EditableDataWindow, AmoebaStory, FlowFieldStory, HeatMapStory, HoneycombStory, NetworkWebStory, PulseWaveStory, SpiralStory, TerrainStory, DashboardEmbed, and GenieChat through the packaged Node process. GenieChat discovery uses the caller token in local contract tests; its generated source uses the viewer token and the installed workspace host. AmoebaStory source preview packages the legacy interactive canvas HTML and uses the shared 100-row entity query; FlowFieldStory uses a 500-row flow query; HeatMapStory uses a 500-row map query; HoneycombStory groups one row per item and uses the shared 100-row cap; NetworkWebStory uses the shared 1,000-edge cap; PulseWaveStory queries ascending periods without a latest filter and uses the shared 500-row cap; SpiralStory groups journeys and milestones, orders by timeline, selects a default journey deterministically, and uses the shared 100-row cap; TerrainStory groups X/Y cells, can filter to the latest time period, and uses one 500-row cap. DashboardEmbed normalizes pasted references to a hostless path and reconstructs its origin from trusted runtime configuration. Current preview is explicitly marked preview-only. Modal source is a named `@st.dialog` definition and workflow `ShowModal` invokes it. Generated Lakebase Autoscaling readers cover DataWindow, all four charts, and all eight stories; local PostgreSQL 17 execution evidence is recorded in the transition handoff. EditableDataWindow writes remain Unity Catalog Delta-only. Other component types return an error instead of being omitted. This local HTTP/package check does not prove Databricks runtime behavior or complete component parity.

For real PostgreSQL migration/repository verification, install PostgreSQL 17 command-line tools (`initdb` and `pg_ctl`) and run `npm run test:postgres`. The script creates a temporary local cluster bound only to `127.0.0.1`, runs migrations plus component and portability aggregate/rollback integration cases, then stops and removes that temporary cluster. The test suite also discovers the integration case and skips it unless `VDAB_TEST_DATABASE_URL` is explicitly set.

## Databricks runtime configuration

Databricks Apps supplies `DATABRICKS_APP_PORT`, `DATABRICKS_HOST`, and `DATABRICKS_WORKSPACE_ID`. Configure Apps user authorization and the documented scopes required by the features enabled for this installation. GenieChat specifically requires the `genie` user authorization scope, configured through the Databricks Apps UI or CLI `user_api_scopes` setting; it is not an `app.yaml` field. Each viewer must consent and have access to the selected Genie space and its underlying data. Workspace operations use the caller's forwarded access token; denied operations do not retry with the app service principal. Local tests and generated fixtures are not evidence of Genie permission or runtime behavior in a workspace. The local test mode must never be enabled in a deployed App.

The `app.yaml` declares the expected `postgres` Lakebase Autoscaling binding. The installed app expects Databricks to inject `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, and `PGSSLMODE`; it also reads `LAKEBASE_ENDPOINT` plus the Apps runtime's `DATABRICKS_CLIENT_ID` and `DATABRICKS_CLIENT_SECRET`. The server obtains a short-lived workspace OAuth token and exchanges it for a short-lived Lakebase password. No static database password is stored. The production app applies versioned, advisory-lock-serialized migrations `001_initial_schema.sql` through `005_project_portability.sql` during startup. A customer administrator must provision and bind a compatible customer-owned resource; VDAB does not create a Lakebase project/database.

Production project routes currently support metadata create/list/read/update, creator-managed editor grants, and an install-admin recovery allowlist. The component subresource supports ordered save/reopen for all 33 retained component type identifiers, including nested stable keys, properties, bindings, and layout. The standalone editor now adds and edits NetworkWebStory and PulseWaveStory field mappings and visualization settings alongside the other implemented component flows. NetworkWebStory preview queries the hosting-workspace Unity Catalog table with the viewer token and embeds the local graph canvas with keyboard-operated filters and node navigation. PulseWaveStory preview validates its six mappings, queries all periods ascending with no latest-period filter, uses one 500-row cap, and embeds the accessible wave/events canvas. EditableDataWindow retains its display and row-mode options, selects a table key column, and allows saves only for Delta tables; non-Delta or unreported formats are read-only. Component properties are type-checked during save/import and again before source generation. Metadata and component saves use project optimistic versions and append audit events in the same transaction. `POST /api/v1/projects/{projectId}/preview` checks the project ACL and emits deterministic preview-only Python for empty projects and the implemented slices; deployment remains unavailable. DataWindow SQL uses the viewer token and requires an existing SQL warehouse; Lakebase Autoscaling DataWindow, chart, and story reads use the generated PostgreSQL runtime; real workspace authorization and child-app execution remain unverified. The generated EditableDataWindow uses a parameterized `MERGE` and checks for null/duplicate key values across the full table before each non-empty save. Databricks does not enforce declared primary-key constraints, and the preflight check and `MERGE` are separate statements, so concurrent table writes remain a limitation. These SQL operations, the viewer's `sql` consent and grants, and generated Streamlit runtime are unverified in a workspace. Legacy integer Modal width and height values remain accepted but do not map to current dialog sizing. Label uses fixed CSS and escapes both saved and overridden text in the generated runtime. Button `onClick`, control `onChange`, and Form `onSubmit` dispatch through the generated workflow runtime, which also executes Modal `ShowModal`. Unity Catalog SQL, table writes, and current-workspace Jobs actions are generated; Lakebase `RunSql` and `SaveToTable` use the generated PostgreSQL runtime and passed local PostgreSQL 17 tests; real workspace authorization remains unverified. The Jobs list and Run Now paths use the forwarded viewer token and trusted workspace host, but the current Apps authorization guide omits `jobs` from its supported user scopes, so actual Apps scope/permission behavior remains unverified. Triggered Jobs execute using their configured Run-as identity. Project data is scoped to the hosting workspace and the Lakebase database bound to that install. Set `VDAB_INSTALL_ADMIN_IDS` in the installed app configuration to a comma-separated list of Databricks user IDs that may recover projects. This is an explicit install-managed allowlist; it does not infer Databricks workspace-admin status. Recovery access is written to the install's audit table. Collaborator access grants VDAB project access only and never grants Databricks resource permissions.

In `local-test` mode, the project and component repositories are in-memory and lose their data on restart. They exist only for offline UI and HTTP smoke tests; they are never used in production. The production Lakebase password flow, resource variable injection, schema permissions, and restart durability have not been tested against a workspace. Do not treat a local smoke run as Lakebase evidence.

## FileUpload and workspace resource discovery

The standalone FileUpload editor supports multiple files, in-memory behavior, and an optional current-workspace Volume destination. In production, the Node resource adapter derives its HTTPS host from `DATABRICKS_HOST` and sends only the caller's forwarded token. The generated Python uses the viewer's token for raw-byte uploads through the Files API; it does not retry with the VDAB service principal. Names and relative paths are validated and encoded.

Local smoke uses a deterministic mock catalog/schema/Volume and verifies route authority rejection, component save/reopen, and generated uploader source. This does not exercise Databricks OAuth consent, Volume scopes/privileges, or the Files API. The current Apps authorization guide lists granular catalog SDK scopes but no Volume-list scope matching the direct Volumes API's documented `unity-catalog` scope; this direct API/scope pairing remains a workspace feasibility gate.

DataWindow's Unity Catalog selector uses the same catalog/schema resource boundary plus paginated table discovery at `/api/v1/workspace/resources/tables?catalogName=…&schemaName=…`. The offline adapter supplies `main.default.customers` and column metadata. Generated DataWindow SQL reads `st.context.headers["x-forwarded-access-token"]` and calls the installed workspace SQL Statement API using `DATABRICKS_SQL_WAREHOUSE_ID`; EditableDataWindow uses the same viewer authorization, sends changed cell values as a named SQL parameter, and runs a single Delta `MERGE`. No generated operation uses the builder or child-App service principal for viewer queries. EditableDataWindow checks key uniqueness/nulls across the table before a non-empty save; this check is separate from the later `MERGE`. The Tables API's direct REST scope pairing with Apps user authorization, SQL warehouse/table grants, DML behavior, and generated Streamlit runtime have not been tested. Lakebase Autoscaling DataWindow reads generate viewer-authorized PostgreSQL queries; local PostgreSQL 17 query execution passed, but Databricks runtime authorization is unverified.

## Standalone project portability

The project list exports one ACL-authorized project as standalone schema v1 and imports a JSON bundle up to 1 MiB. Import rejects SaaS/authority/secret-bearing documents, validates components, workflows, and custom modules before persistence, and creates the project under the importing user. Workspace-local resource identities are cleared and returned with their usage locations for reselection; the target child App must also be selected before deployment. Lakebase persists the project, components, workflows, unresolved references, and import audit event atomically. Focused UI/API/HTTP tests and PostgreSQL transaction/rollback tests pass locally. This feature has not been exercised in a Databricks workspace.

## ModelChat endpoint authorization

ModelChat lists endpoints in the workspace hosting VDAB and stores only the selected endpoint name and display settings. For deployed Apps, configure the supported `model-serving` user authorization scope in the Databricks Apps UI or the `user_api_scopes` CLI setting. Every child-app viewer must have query permission on the selected endpoint. Generated ModelChat requests use the viewer's forwarded access token and trusted workspace host, reject redirects, and never fall back to the App service principal. The serving invocation API documents chat fields as Public Preview and lists `model-serving-inference` as an additional scope; the current Apps guide does not list that scope. Validate this scope pairing, endpoint compatibility, and runtime behavior in a disposable workspace before enabling ModelChat for customers. This repository's local adapter and smoke are not workspace evidence.

Generated Python/Streamlit readers cover DataWindow, all four charts, and all eight story types; workflow `RunSql` and `SaveToTable` use caller-scoped Lakebase credentials and parameterized PostgreSQL. Child-App create/link/deploy routes are not implemented, and generated output is still preview-only. No Databricks workspace was accessed, so App proxy identity, OAuth scopes/roles, Apps deployment, Lakebase durability, generated Streamlit execution, child-App lifecycle, and Marketplace installation remain unverified. StartDatabricksJob discovery and generated Run Now also use the viewer token; job IDs are validated as positive int64 values and Databricks checks the viewer's run permission. The triggered job still executes under its configured Run-as identity, and the Apps-specific `jobs` scope is unverified because it is omitted from the current Apps supported-scope list. The legacy external-connection editor remains available in the temporary source tree.
