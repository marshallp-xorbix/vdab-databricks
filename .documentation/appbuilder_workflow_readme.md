# App Builder Workflow System

## Purpose

This document defines the workflow system contracts, implementation locations, and wiring responsibilities for the App Builder workflow domain.

It is limited to:

- available workflow actions
- persisted workflow contracts
- workflow editor composition
- workflow validation and metadata integration
- backend runtime generation and service registration
- file ownership and system organization

It does not describe implementation history, migration work, or release planning.

## Available Actions

Only these actions are part of the workflow contract:

- `TriggerToast`
- `ShowModal`
- `SaveToTable`
- `BuildSql`
- `RunSql`
- `SetBinding`
- `StartDatabricksJob`

## Persisted Workflow Contracts

### Workflow definition

```ts
interface WorkflowDefinition {
	version: 1;
	workflows: Workflow[];
}

interface Workflow {
	codeName: string;
	trigger: WorkflowTrigger;
	nodes: WorkflowActionNode[];
	edges: WorkflowEdge[];
}

interface WorkflowTrigger {
	componentCodeName: string;
	eventKey: string;
}

interface WorkflowEdge {
	fromNodeId: string;
	toNodeId: string;
	route: WorkflowRoute;
}

type WorkflowRoute = "onSuccess" | "onError" | "always";
```

### Base action node

```ts
interface BaseActionNode<TActionType extends string, TParams> {
	id: string;
	actionType: TActionType;
	schemaVersion: 1;
	params: TParams;
}
```

### Workflow action union

```ts
type WorkflowActionNode =
	| TriggerToastNode
	| ShowModalNode
	| SaveToTableNode
	| BuildSqlNode
	| RunSqlNode
	| SetBindingNode
	| StartDatabricksJobNode;
```

## Frontend Wiring

The frontend workflow editor is wired together as follows:

1. `AppBuilder.tsx` renders `WorkflowBuilderView.tsx` in workflow mode and passes `WorkflowDefinition`, components, and `onChange`.
2. `WorkflowBuilderView.tsx` builds graph nodes/edges and owns workflow-level mutation functions (workflow add/remove, node/edge updates, route updates).
3. `WorkflowBuilderView.tsx` passes the active selection and mutation callbacks into `WorkflowSelectionPanel.tsx`.
4. `WorkflowSelectionPanel.tsx` routes editing to `WorkflowTriggerEditor.tsx` (trigger), `WorkflowNodeEditor.tsx` (action), or inline edge route controls (edge).
5. `WorkflowNodeEditor.tsx` resolves the selected action through `ActionRegistry.ts`, renders the dedicated action editor, and shows validation errors from `validateActionNode.ts`.
6. `registry/actionDefaults.ts` supplies a strict default node shape whenever a new node is created or an action type is changed.
7. `editors/actions/*` update only their strict action-specific params.
8. `utils/workflow/*` supplies graph-aware selectors, placeholder synchronization, SaveToTable source discovery, and editor-time validation.
9. `DatabricksDataConnectorApi.ts` provides job and table metadata needed by action editors that integrate with Databricks resources.

Persisted workflow documents enter the backend as DTOs, then get parsed into typed workflow models before generator dispatch.

Transport input:

```text
Xorbix-Visual-Databricks-App-Builder.Models/
	DTOs/Workflow/
	DTOs/BuilderComponents/
```

Typed generation and validation models:

```text
Xorbix-Visual-Databricks-App-Builder.Models/
	Workflow/
		WorkflowDefinitionModel.cs
		WorkflowModel.cs
		WorkflowActionNodeModel.cs

		SharedReferences/
```

Current backend flow:

- DTOs are the transport layer received by `StreamlitTemplateService.cs`.
- `WorkflowDefinitionParser.cs` and `WorkflowActionParser.cs` convert those DTOs into typed workflow models.
- `WorkflowTemplateValidator.cs` validates the typed workflow model against component data and action rules.
- `WorkflowTemplateHelper.cs` dispatches generators using typed action model matching through `IWorkflowActionGenerator<TActionNode>`.

## Backend Wiring

The backend workflow runtime is wired together as follows:

1. `Xorbix-Visual-Databricks-App-Builder.Services/ServiceCollectionExtensions.cs` calls `AddWorkflowServices()`.
2. `Workflow/ServiceCollectionExtensions.cs` registers workflow action definitions, validation services, `IWorkflowTemplateHelper`, and all `IWorkflowActionGenerator` implementations.
3. `StreamlitTemplateService.cs` depends on `IWorkflowTemplateHelper`.
4. `StreamlitTemplateService.cs` calls `Validate(...)`, parses the workflow for import and dependency decisions, and then calls `AppendRuntime(...)` while building the Streamlit output.
5. `WorkflowTemplateValidator.cs` parses DTO input into typed workflow models and then runs orchestration, structure, action, and reference validation.
6. `WorkflowTemplateHelper.cs` re-parses validated DTO input into typed workflow models, emits shared workflow runtime helpers, builds each workflow handler, and resolves the generator implementation for each action node through the registered `IWorkflowActionGenerator` collection.
7. `WorkflowTemplateHelper.cs` pattern-matches each typed action node and dispatches only generators whose `ActionKind` and `ActionModelType` both match.
8. Each action generator writes the runtime execution block for its corresponding typed action type.

### Current backend runtime notes

- `BuildSqlActionGenerator.cs` reads placeholder values from `st.session_state` using `componentCodeName`, formats them from typed `valueType` and optional `formatHint`, and emits `output.sql` plus `output.sqlSourceKind`.
- `RunSqlActionGenerator.cs` currently resolves the referenced `BuildSql` node's `output.sql` and executes it through `sql_query_df(...)` (app service principal) for Unity Catalog, or Lakebase helpers for Postgres sources.
- `SetBindingActionGenerator.cs` currently resolves `RunSql` `output.rows` and writes the result into `binding_overrides`.
- `SaveToTableActionGenerator.cs` currently builds an `INSERT INTO ... VALUES (...)` statement from explicit column mappings, then executes it through `sql_execute(...)` for Unity Catalog targets or `lakebase_execute_sql(...)` for Lakebase targets.

## Validation Responsibilities

### Frontend validation

Frontend validation is editor-time validation intended to guide configuration before persistence.

It includes:

- BuildSql placeholder-to-component validation
- RunSql graph-reachable source validation
- SetBinding graph-reachable source validation
- SetBinding target component and binding-type validation
- ShowModal modal target validation
- SaveToTable trigger-form and source component validation
- StartDatabricksJob required job selection validation

### Backend validation

Backend validation is generation-time validation intended to protect runtime generation.

It includes:

- workflow DTO-to-model parsing
- workflow code name validation
- unique workflow code name enforcement
- trigger component and trigger event validation
- duplicate trigger prevention
- edge-to-node reference validation
- action-specific validation for modal references, BuildSql placeholder metadata, table save targets, binding references, and Databricks job configuration
- prior-node reference validation for `RunSql` and `SetBinding`, with earlier-node-order fallback when no edge path exists

## Metadata Resolution Responsibilities

The workflow system uses Databricks metadata for editor-time configuration in these areas:

- `StartDatabricksJob` resolves job choices from Databricks jobs.
- `SaveToTable` resolves Unity Catalog table metadata through `getUnityCatalogTableDetails(...)`.
- `SaveToTable` resolves Lakebase editor metadata through Lakebase selector state, then uses the synced Unity Catalog catalog, schema, and table with `getUnityCatalogTableDetails(...)` to retrieve column metadata.

Metadata resolution is not itself part of the persisted workflow document. Persisted workflow nodes store references only.

## Contract Rules

- Frontend workflow documents use `version: 1`.
- Every workflow action node uses `schemaVersion: 1`.
- Persisted workflow nodes use strict action-specific param contracts.
- Workflow edges use only the persisted route values defined by `WorkflowRoute`.
- `RunSql` stores a `BuildSql` node reference in `statement.nodeId`.
- `SetBinding` stores a `RunSql` node reference in `source.nodeId`.
- `StartDatabricksJob` stores `jobId` as a string.
- `SaveToTable` stores explicit table references, excluded-column overrides, and explicit column mappings.
- The action registry is the authoritative frontend source for available workflow actions and their editor components.
- The workflow action definition registry is the authoritative backend source for action-specific validation by action type.
- The workflow action generator registry is the authoritative backend source for runtime generation by action type and typed action model.

## Route Policy

Supported workflow routes are:

- `onSuccess`
- `onError`
- `always`

Persisted route values must use the route contract exactly.
