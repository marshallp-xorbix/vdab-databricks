# Authentication & Identity System

VDAB uses ASP.NET Core Identity with custom authentication flows supporting both traditional password-based and passwordless email authentication.

## Data Protection & Encryption

The application uses **ASP.NET Core Data Protection** to secure sensitive data (auth tokens, cookies, password reset tokens).

### Architecture
- **Key Storage:** Data Protection keys are persisted to an XML file in a dedicated Azure Blob Storage container (`keys/keys.xml`).
- **Key Encryption:** The XML file itself is encrypted at rest using a master **RSA Key** stored in Azure Key Vault (`DataProtectionKey`).
- **Access Control:** The App Service uses its Managed Identity to access both the Storage Account and Key Vault.

### Configuration
The system requires the following configuration (automatically handled via Key Vault in production):
- `Encryption:BlobUri`: URI to the blob storage container.
- `Encryption:KeyUri`: URI to the Key Vault RSA key.

This setup ensures that:
1. Keys persist across application restarts and deployments.
2. Keys are shared across all instances in a scaled-out environment (preventing "Invalid Token" errors).
3. The master encryption key is securely managed in hardware security modules (HSM) via Key Vault.

## Authentication Flow

### Authentication Methods

1. **Traditional Registration & Login** (Primary)
   - Email + password registration with email confirmation
   - Standard login with credentials
   - Password reset flow

2. **Passwordless Authentication** (Available)
   - Email-based verification codes (6-digit)
   - No password required for sign-in
   - 2FA support for enhanced security

3. **API Key Authentication** (Service-to-Service)
   - Header-based: `X-API-Key`
   - For automated integrations

### Tech Stack

- **ASP.NET Core Identity** - User management
- **JWT Bearer Tokens** - API authentication
- **Azure Communication Service** - Email delivery (see `.infrastructure/COMMUNICATION_SERVICE_SETUP.md`)
- **Distributed Cache** - Verification code storage (MemoryCache/Redis)
- **FluentResults** - Error handling pattern

## Authentication Workflows

See `IdentityController.cs` for API implementation details.

### 1. Traditional Registration Flow

**New User Registration with Email Confirmation:**

1. User submits registration form with email, password, first name, and last name
2. System creates user account with `Developer` role by default
3. Email confirmation link sent to user's email address
4. User clicks confirmation link with token
5. System validates token and confirms email address
6. User can now log in

**Implementation Details:**
- Delegates to `AuthService.RegisterAsync()` → `UserService.CreateUserAsync()`
- Default role: `AuthRoles.Developer`
- Token generated by `UserManager.GenerateEmailConfirmationTokenAsync()`
- Returns success for duplicate emails (prevents user enumeration)
- Logs IP address and user agent for security auditing

**Security Features:**
- One-time use tokens
- Tokens stored in database and validated server-side
- Option to resend confirmation email if lost

### 2. Password-Based Login Flow

**Standard Authentication:**

1. User submits email and password
2. System validates credentials against database
3. If 2FA enabled, sends verification code to email
4. User submits 2FA code (if required)
5. System issues JWT access token and refresh token
6. Client stores tokens for subsequent API calls

**Authentication Response:**
```json
{
  "accessToken": "eyJhbGc...",
  "refreshToken": "...",
  "expiresAt": "2025-11-24T13:30:00Z",
  "user": {
    "id": 1,
    "email": "user@example.com",
    "firstName": "John",
    "lastName": "Doe",
    "roles": ["Developer"]
  },
  "requiresTwoFactor": false,
  "twoFactorExpiresAt": null
}
```

**Security Features:**
- Email confirmation required (configurable)
- Account lockout after 5 failed attempts (15 minutes)
- 2FA support with time-limited verification codes
- Comprehensive authentication event logging

### 3. Passwordless Authentication Flow

**Email-Based Verification Code Login:**

1. User submits email address to initiate passwordless sign-in
2. System generates 6-digit numeric verification code
3. Code stored in distributed cache with 5-minute TTL
4. Verification code sent to user's email
5. User submits email and verification code to unified verification endpoint
6. System validates code and issues JWT tokens

**Note:** The verification code endpoint (`verify-code`) is unified to handle both passwordless authentication and 2FA verification during traditional login.

**Security Features:**
- Maximum 3 verification attempts per code
- Code expires after 5 minutes
- Code invalidated after successful use
- Attempt tracking in cache
- Always returns success on initiation (prevents enumeration)

### 4. Password Reset Flow

**Forgot Password:**

1. User submits email address for password reset
2. System generates password reset token
3. Reset link with token sent to email (if user exists)
4. User clicks reset link and submits new password with token
5. System validates token and updates password
6. User can log in with new password

**Security Features:**
- Always returns success (prevents user enumeration)
- Time-limited reset tokens
- One-time use tokens
- Old password immediately invalidated

### 5. Token Refresh Flow

**Maintaining Session:**

1. Client detects JWT access token approaching expiration
2. Client sends refresh token to refresh endpoint
3. System validates refresh token against database
4. System issues new JWT access token and new refresh token
5. Old refresh token revoked
6. Client updates stored tokens

**Token Management:**
- Access tokens: Short-lived (configurable, typically 15-60 minutes)
- Refresh tokens: Longer-lived, stored in database
- Refresh tokens revoked on logout
- Refresh tokens can be revoked by admin (security stamp update)

### 6. Profile & Email Management

**Change Password (Authenticated Users):**
- User must provide current password
- New password must meet security requirements
- System automatically forces logout on all devices after password change
- Security stamp updated to invalidate all existing tokens
- User must log in again with new password

**Change Email:**
1. User submits new email and current password
2. System sends confirmation email to new address
3. User clicks confirmation link with token
4. System validates token and updates email
5. System automatically forces logout on all devices after email change
6. Old email remains active until confirmation

**Update Profile:**
- Users can update first name and last name
- Email changes require separate confirmation flow
- Password changes and email changes trigger automatic logout for security

### 7. Two-Factor Authentication

**Enable 2FA:**
- User enables 2FA on their account
- System updates user settings

**2FA Login Flow:**
1. User submits email and password
2. System validates credentials
3. System generates 6-digit code and sends to email
4. User submits verification code
5. System validates code and issues JWT tokens

**Disable 2FA:**
- User can disable 2FA on their account
- Returns to standard password-only login

### 8. Logout & Session Management

**User-Initiated Logout:**
- User calls logout endpoint
- System revokes all refresh tokens for user
- System updates security stamp to invalidate all JWT tokens
- Client discards JWT access token
- User logged out on all devices
- User must log in again to access system

**Admin-Initiated Force Logout:**
- Admin calls force logout endpoint for target user
- System updates user's security stamp
- System revokes all refresh tokens
- Invalidates all existing JWT tokens across all devices
- Target user must log in again on all devices

## Authentication Configuration

### JWT Bearer Settings

Configured in `ServiceDefaults/AuthenticationExtensions.cs`:

```csharp
.AddJwtBearer(options =>
{
    options.TokenValidationParameters = new TokenValidationParameters
    {
        ValidateIssuer = true,
        ValidateAudience = true,
        ValidateLifetime = true,
        ValidateIssuerSigningKey = true,
        ValidIssuer = jwtConfig.Issuer,
        ValidAudience = jwtConfig.Audience,
        IssuerSigningKey = new SymmetricSecurityKey(
            Encoding.UTF8.GetBytes(jwtConfig.SecretKey)),
        ClockSkew = TimeSpan.Zero
    };
});
```

**Token Claims:**
- `sub` / `NameIdentifier` — User's database ID (`Guid`)
- `Email` — User's email address
- `Name` — Username
- `GivenName` / `Surname` — First and last name
- `role` — Global roles (for example `Administrator`, `Developer`)
- `tenant_id` — Active tenant context (`Guid`); present after login or tenant switch
- `tenant_role` — User's role within the active tenant (`Admin`, `Developer`)

**Active tenant context:** For authenticated API calls, the active tenant is always the `tenant_id` claim in the JWT — not `ApplicationUser.TenantId` (home/owning tenant) and not the database last-accessed/default-tenant fallback. Controllers read identity via `AuthenticatedControllerBase` (`RequireAuthenticatedContext`, `RequireAuthenticatedUser`, `AuthenticatedUserId`, `AuthenticatedTenantId`); services receive `userId` / `tenantId` as explicit parameters from the controller. Profile and account-setup endpoints prefer JWT tenant claims when present.

**Token Lifetimes:**
- Access Token: 60 minutes (configurable via `JwtConfiguration__ExpirationMinutes`)
- Refresh Token: 7 days (configurable via `JwtConfiguration__RefreshTokenExpirationDays`)

### Identity Options

```csharp
builder.Services.AddIdentity<ApplicationUser, IdentityRole<int>>(options =>
{
    // Password requirements
    options.Password.RequireDigit = true;
    options.Password.RequireUppercase = true;
    options.Password.RequireNonAlphanumeric = true;
    options.Password.RequiredLength = 8;
    
    // Lockout (prevents brute force)
    options.Lockout.DefaultLockoutTimeSpan = TimeSpan.FromMinutes(15);
    options.Lockout.MaxFailedAccessAttempts = 5;
    options.Lockout.AllowedForNewUsers = true;
    
    // User settings
    options.User.RequireUniqueEmail = true;
    options.SignIn.RequireConfirmedEmail = false; // Set true when email service is configured
});
```

### Authorization Policies

Defined in `ServiceDefaults/AuthenticationExtensions.cs`:

```csharp
// API Access - JWT or API Key
services.AddAuthorizationBuilder()
    .AddPolicy("ApiAccess", policy =>
    {
        policy.AuthenticationSchemes.Add(JwtBearerDefaults.AuthenticationScheme);
        policy.AuthenticationSchemes.Add("ApiKey");
        policy.RequireAuthenticatedUser();
    })
    
    // Role-based policies (JWT only)
    .AddPolicy(AuthPolicies.RequireAdministratorRole, policy =>
        policy.RequireRole(AuthRoles.Administrator))
    
    .AddPolicy(AuthPolicies.RequireTenantAdminRole, policy =>
        policy.RequireRole(AuthRoles.TenantAdmin, AuthRoles.Administrator))
    
    .AddPolicy(AuthPolicies.RequireManagerRole, policy =>
        policy.RequireRole(AuthRoles.Manager, AuthRoles.TenantAdmin, AuthRoles.Administrator))
    
    .AddPolicy(AuthPolicies.RequireDeveloperRole, policy =>
        policy.RequireRole(AuthRoles.Developer, AuthRoles.Manager, 
                           AuthRoles.TenantAdmin, AuthRoles.Administrator));
```

**Role Hierarchy:**
- **Administrator** (Level 4) - Full system access
- **TenantAdmin** (Level 3) - Tenant-wide administration
- **Manager** (Level 2) - User and settings management
- **Developer** (Level 1) - Workflow creation and modification

**Authorization Rules:**
- Users can only modify other users with equal or lower role levels
- Role assignments require equal or higher role level
- Implemented via `UserExtensions.CanModifyUser()` and `UserExtensions.CanManageRoles()`

**Usage in Controllers:**
```csharp
[Authorize] // Requires JWT authentication
[Authorize(Policy = AuthPolicies.RequireManagerRole)] // Requires Manager, TenantAdmin, or Admin role
[AllowAnonymous] // Public endpoint

// In code - check if user can modify another user
if (!User.HasElevatedPermissions()) { return Forbid(); }
if (!User.CanModifyUser(targetUserRoles)) { return Forbid(); }
```

## Services

### `IAuthService` (`AuthService.cs`)

Core authentication service handling user registration, login, and passwordless flows.

**Key Methods:**
- `RegisterAsync(request, confirmationUrl, ipAddress, userAgent)` - Register new user
- `ConfirmEmailAsync(userId, token)` - Confirm email address
- `LoginAsync(email, password, ipAddress, userAgent)` - Traditional login
- `SendVerificationCodeAsync(email, user?)` - Send verification code (2FA or passwordless)
- `VerifyCodeAndAuthenticateAsync(email, code, ipAddress, userAgent)` - Verify code & authenticate
- `ForceLogoutAllDevicesAsync(userId)` - Force logout on all devices
- `ChangePasswordAsync(userId, currentPassword, newPassword)` - Change password
- `ForgotPasswordAsync(email, resetUrl)` - Initiate password reset
- `ResetPasswordAsync(email, token, newPassword)` - Reset password with token
- `ResendConfirmationEmailAsync(email, confirmationUrl)` - Resend confirmation email
- `Enable2FAAsync(userId, initiatedByUserId?)` - Enable two-factor authentication
- `Disable2FAAsync(userId, initiatedByUserId?)` - Disable two-factor authentication
- `ConfirmEmailChangeAsync(userId, newEmail, token)` - Confirm email change
- `RefreshTokenAsync(refreshToken, ipAddress, userAgent)` - Refresh access token

**Dependencies:**
- `UserManager<ApplicationUser>` - User management
- `SignInManager<ApplicationUser>` - Sign-in operations
- `IJwtService` - Token generation
- `IEmailSenderService` - Email delivery
- `IDistributedCache` - Verification code storage
- `IUserService` - User operations

### `IJwtService` (`JwtService.cs`)

Handles JWT token generation and validation.

**Methods:**
- `GenerateAccessTokenAsync(user, roles)` - Create JWT access token
- `GenerateRefreshToken()` - Create refresh token (cryptographically random)
- `ValidateRefreshToken(token)` - Validate refresh token

**Token Storage:**
- Access tokens: Stored client-side only
- Refresh tokens: Stored in `RefreshTokens` table with user association

### `IUserService` (`UserService.cs`)

User management operations.

**Methods:**
- `CreateUserAsync(email, firstName, lastName, roles, setupUrl, password?, sendWelcomeEmail, usePasswordlessLogin, createdByUserId)` - Create user
- `GetCurrentUserInfoAsync(userId)` - Get user profile
- Additional CRUD operations

### `IEmailSenderService` (`EmailSenderService.cs`)

Email delivery using Azure Communication Service.

**Methods:**
- `SendVerificationCodeAsync(user, email, code, expiresAt)` - Passwordless code email
- `SendWelcomeEmailAsync(user, email, setupUrl)` - Welcome email with confirmation link
- Uses HTML templates from `EmailTemplates/` directory

**Configuration:**
- Connection string in App Settings (from Key Vault in Azure)
- See `.infrastructure/COMMUNICATION_SERVICE_SETUP.md` for setup

## Security Best Practices

### Implemented

✅ **Password Hashing** - Identity's default PBKDF2 with salt  
✅ **JWT Signing** - HS256 with secret from Key Vault  
✅ **HTTPS Only** - Enforced in production  
✅ **Account Lockout** - 5 attempts, 15 min lockout  
✅ **Email Confirmation** - Required before login (configurable)  
✅ **Audit Logging** - IP address, user agent tracked  
✅ **Enumeration Prevention** - Same response for invalid/existing emails  
✅ **Time-Limited Codes** - 5-minute expiration, max 3 attempts  
✅ **CORS** - Configured origins only

## Client Integration

### Login Flow

```typescript
// 1. Login
const response = await fetch(`${API_BASE_URL}/api/identity/login`, {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ email, password })
});

const { accessToken, refreshToken, user, requiresTwoFactor, twoFactorExpiresAt } = await response.json();

// 2. If 2FA required, verify code
if (requiresTwoFactor) {
  const code = prompt('Enter verification code from email');
  const verifyResponse = await fetch(`${API_BASE_URL}/api/identity/verify-code`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ email, code })
  });
  const verifiedAuth = await verifyResponse.json();
  accessToken = verifiedAuth.accessToken;
  refreshToken = verifiedAuth.refreshToken;
}

// 3. Store tokens
localStorage.setItem('accessToken', accessToken);
localStorage.setItem('refreshToken', refreshToken);

// 4. Use token in subsequent requests
fetch(`${API_BASE_URL}/api/resource`, {
  headers: { 'Authorization': `Bearer ${accessToken}` }
});
```

### Passwordless Flow

```typescript
// 1. Request code
await fetch(`${API_BASE_URL}/api/identity/passwordless/login`, {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ email })
});

// 2. User enters code from email
const response = await fetch(`${API_BASE_URL}/api/identity/verify-code`, {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ email, code })
});

const { accessToken, refreshToken, user } = await response.json();

// 3. Store tokens
localStorage.setItem('accessToken', accessToken);
localStorage.setItem('refreshToken', refreshToken);
```

### Token Refresh Flow

```typescript
// Refresh token before expiration
const response = await fetch(`${API_BASE_URL}/api/identity/token/refresh`, {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ refreshToken: localStorage.getItem('refreshToken') })
});

const { accessToken, refreshToken: newRefreshToken } = await response.json();
localStorage.setItem('accessToken', accessToken);
localStorage.setItem('refreshToken', newRefreshToken);
```

### Logout Flow

```typescript
// Logout - revokes all refresh tokens and invalidates sessions
await fetch(`${API_BASE_URL}/api/identity/logout`, {
  method: 'POST',
  headers: { 
    'Authorization': `Bearer ${localStorage.getItem('accessToken')}`,
    'Content-Type': 'application/json'
  }
});

// Clear local storage
localStorage.removeItem('accessToken');
localStorage.removeItem('refreshToken');
```

## Troubleshooting

### Email Confirmation Not Working
- Check Azure Communication Service configuration
- Verify connection string in App Settings
- Review Application Insights for email send errors
- See `.infrastructure/COMMUNICATION_SERVICE_SETUP.md`

### JWT Token Invalid
- Verify `JwtConfiguration__SecretKey` in Key Vault matches issuer
- Check token expiration (`expiresAt` field)
- Ensure `Issuer` and `Audience` match configuration

### Account Locked Out
- Wait 15 minutes or clear lockout via database:
```sql
UPDATE iam.AspNetUsers 
SET LockoutEnd = NULL, AccessFailedCount = 0 
WHERE Email = 'user@example.com';
```

### Verification Code Not Received (2FA or Passwordless)
- Check email service logs in Application Insights
- Verify code exists in cache (expires after 5 min)
- Ensure user account exists and is active
- For passwordless: Ensure `UsePasswordlessLogin` flag is true for user
- Check spam/junk folder for verification email

### User Logged Out Unexpectedly
- Security stamp may have been updated (password change, email change, or admin action)
- Refresh tokens are revoked when security stamp is updated
- User must log in again to obtain new tokens
