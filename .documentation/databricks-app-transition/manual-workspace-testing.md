3. Include an existing Provisioned binding. Confirm its `valueFrom` value resolves to the selected instance host, the generated runtime checks that host against instance metadata, and reads/writes request viewer-scoped credentials for that instance/database.
4. Link an existing App with an exact matching resource set and deploy. Repeat with a default-key resource such as `postgres`/`database`, a missing database, an extra database, and the correct key bound to the wrong database. Verify only the exact match is accepted and rejected cases have no source-upload/deployment side effects.
5. Retry a failed deployment and restore the last successful source snapshot. Confirm resource keys and bindings remain stable through retry, restart, update, and rollback. Record only resource labels and result codes; do not record endpoint paths, hosts, credentials, or tokens.

Databricks exposes child-App standard output, error, and system/build/access logs through its Logs tab and, while the App is running, the App URL's `/logz` path. VDAB links to this supported view instead of proxying or retaining customer App logs: [Logging and Monitoring for Databricks Apps](https://docs.databricks.com/aws/en/dev-tools/databricks-apps/monitor).

## Update, rollback, and uninstall

1. Deploy a new builder package over existing Lakebase data. Confirm migrations are append-only, project state remains intact, and a fresh App process can use it.
2. Stop/restart the App and verify the app and project behavior after startup. Separately export a project and create a Lakebase database backup; confirm operators understand that project JSON does not include deployment history or saved child source snapshots.
3. Configure the Lakebase root-branch history window and a snapshot schedule that meets the data owner's retention policy. Record cadence, retention, expected snapshot cost acceptance, and backup owner without recording customer data.
4. Create a pre-migration snapshot, restore it to a new branch, and validate the restored schema and representative project/deployment rows. Confirm the current branch remains unchanged and that the owner has a reviewed cutover procedure. Test `pg_dump`/`pg_restore` against a separate target when the customer requires a copy outside Lakebase.
5. Roll back a builder release from the prior package and verify data/schema compatibility. Roll back a child App to the latest successful immutable source snapshot.
6. Uninstall the builder only after exporting needed projects and making any required Lakebase backup. Confirm Lakebase state, child Apps, per-user child source folders, and resource grants remain or are removed as planned. If removing a Lakebase resource, verify the operator has `CAN MANAGE` or record the manual role/object cleanup owner.

Use the [backup and recovery procedure](../../databricks-app/DEPLOYMENT.md#backup-recovery-and-uninstall). Lakebase point-in-time and snapshot restore create a new branch rather than rewinding the existing branch. Confirm current scope and availability from the official [backup and restore](https://docs.databricks.com/aws/en/oltp/projects/backup-methods), [snapshot](https://docs.databricks.com/aws/en/oltp/projects/snapshots), [pg_dump/pg_restore](https://docs.databricks.com/aws/en/oltp/projects/pg-dump-restore), and [Lakebase DR](https://docs.databricks.com/aws/en/oltp/projects/disaster-recovery) docs before the drill.

## Marketplace publication gates
