# Replace external workspace connections with the installed workspace

**Decision D19:** Every retained builder feature that currently takes `workspaceConnectionId`, `DatabricksConnectionId`, or a selected workspace URL resolves against the workspace hosting this VDAB App. The browser must never choose or supply a Databricks host. The server obtains current-workspace context from the trusted Databricks App runtime and uses the acting user's scoped token for user-triggered calls. The builder app's service principal is reserved for narrow shared/background tasks. Local development uses an explicitly configured mock/current-workspace adapter.

## Required contract and data checks

1. Search the full repository for `workspaceConnectionId`, `WorkspaceConnectionId`, `DatabricksConnectionId`, `workspaceUrl`, saved refresh-token keys, and connection-import/export UI. Classify every hit before deletion; the table above is a starting map, not an exhaustive grep result.
2. The new server rejects or ignores a client-supplied workspace host; Databricks API base URL is derived from trusted runtime configuration. The current workspace URL may be returned for display and dashboard-link validation.
3. New project, component, workflow, AI, and deployment contracts contain no external connection identifier. A workspace-owned resource reference still contains its resource ID/name and type.
4. Test every selector and builder action with an authorized user, a user lacking resource access, missing OAuth consent, and an empty resource list. Test standalone import into a second workspace and require resource reselection before deployment.
5. Generated child apps remain Python/Streamlit and use viewer authorization for user-initiated SQL/Job operations; builder identity must not be copied into generated code or resource grants.

## Current Databricks Apps scope evidence (2026-10-16)

The current [Databricks Apps authorization guide](https://docs.databricks.com/aws/en/dev-tools/databricks-apps/auth) lists API scopes and catalog SDK scopes, but omits `jobs` even though it describes Jobs as a user-authorization use case. The generic [API scopes reference](https://docs.databricks.com/api/workspace/scopes) and [Jobs Run Now API](https://docs.databricks.com/api/jobs/v2/run-now) require the `jobs` scope. The editor and generated code use a current-workspace Jobs list and submit Run Now with the forwarded viewer token, but this does not prove that an Apps user token can receive `jobs`; validate this with an authorized workspace test before release. A bound Jobs App resource grants the App service principal permissions, not a viewer-specific grant, so VDAB must not use it after viewer authorization fails. A viewer with `Can Manage Run` may start the job, while the job's data access still follows its configured Run-as identity. See [Jobs scope and Run-as research](./research.md#startdatabricksjob-authorization-and-run-as-identity--checked-2026-10-20). There is no service-principal fallback for user-initiated operations.

For APIs implemented through Databricks SDKs, the SDK scope names above are the current documented options. For direct REST calls, confirm the exact scope requirement against the target endpoint and runtime. Scope support, endpoint-level permission, and resource access are separate conditions; a listed scope alone is not proof that an ordinary VDAB editor can perform the operation. Record the tested `user_api_scopes`, consent state, HTTP response, user role, and resource grants in `spike-results.md`.

## FileUpload resource discovery and upload — locally implemented, Databricks unverified (2026-10-19)

The FileUpload selector calls `GET /api/v1/workspace/resources/catalogs`, `/schemas?catalogName=...`, and `/volumes?catalogName=...&schemaName=...`. The Node adapter pins HTTPS calls to `DATABRICKS_HOST`, forwards only the acting user's access token, follows pagination, and sanitizes 401/403/upstream failures. It rejects client-supplied host/workspace authority and never retries a denied call as the App identity. The local adapter returns mock names and is only for offline UI/package smoke.

Generated FileUpload code reads Streamlit's forwarded user token and sends raw bytes with `PUT /api/2.0/fs/files/Volumes/<catalog>/<schema>/<volume>/<relative-folder>/<safe-filename>`. Apps authorization documents `files` as a supported scope for Files API operations and granular catalog SDK scopes; the direct Volume list endpoint requires `unity-catalog`, which is absent from the Apps guide's supported scope list. Direct API scope pairing, user consent, and ordinary-user grants (`USE CATALOG`, `USE SCHEMA`, `READ VOLUME` for discovery, `WRITE VOLUME` for upload) remain unproven in an installed VDAB app because the user directed this continuation to remain offline. Never interpret local adapter or generated source tests as Databricks permission evidence.

## Builder Lakebase binding implementation status

The VDAB install uses the `postgres` App resource binding for its own customer-owned Autoscaling database. The App process reads the documented `PG*` connection variables and the `LAKEBASE_ENDPOINT` value mapped from the resource. It obtains the App service-principal OAuth token from `DATABRICKS_CLIENT_ID` / `DATABRICKS_CLIENT_SECRET`, then exchanges that token for an expiring Lakebase credential. The credential is passed only to the `pg` password callback, cached until five minutes before expiry, and never returned or logged. No forwarded user token is used for builder-owned project persistence; per-user tokens remain reserved for user-initiated workspace operations.

The initial schema scopes every project and audit record to the runtime workspace ID and omits SaaS tenant, saved connection, and credential columns. This source implementation passed fake-backed token, migration, ACL, audit, and HTTP tests. The App-specific resource injection, Lakebase role grants, real migration, and restart/redeploy durability are unverified because no workspace/database connection was made.

## DataWindow Unity Catalog source binding — locally implemented, Databricks unverified (2026-10-19)

The standalone DataWindow editor selects a current-workspace catalog, schema, and table through Node routes and stores only resource names plus returned column metadata. `GET /api/v1/workspace/resources/tables?catalogName=…&schemaName=…` calls the installed workspace's Unity Catalog Tables API with the acting user's forwarded token and follows `next_page_token` until absent. It validates workspace-returned table/column metadata and never accepts a host, workspace, or credential from the browser. The local adapter uses fixed sample metadata and does not make a Databricks call.

Generated source reads the viewer token from `st.context.headers["x-forwarded-access-token"]`, uses the runtime `DATABRICKS_HOST`, and requires `DATABRICKS_SQL_WAREHOUSE_ID` to be supplied from an existing child-app SQL warehouse resource. It submits a read-only SQL Statement API request, polls pending/running statements, retrieves inline result chunks, and renders the dataframe with the saved display options. The warehouse resource grants the child App identity warehouse access, but the generated query still uses the viewer token to preserve D16; it does not switch to the service principal after any denial. The builder's current `app.yaml` does not configure this child-app warehouse resource because deployment generation is a later slice.

The direct Tables API documents `unity-catalog`; Apps authorization documents the `catalog.tables:read` SDK scope and the `sql` API scope. Whether an App configured for the SDK scope can use this direct REST endpoint, along with consent, SQL warehouse and table grants, and statement result behavior, remains unverified without the user-authorized workspace test. No fallback scope or app identity is assumed. Lakebase Autoscaling DataWindow execution has separate local PostgreSQL evidence above, but no Databricks workspace evidence.

## EditableDataWindow Unity Catalog Delta binding — locally implemented, Databricks unverified (2026-10-19)

EditableDataWindow reuses the current-workspace table and column selector, adds a required selected key column for complete Delta bindings, and preserves its row mode, disabled state, dimensions, and table display settings. A generated app reads and saves through the viewer's forwarded token and an existing SQL warehouse; row values are sent as one named JSON SQL parameter and merged atomically into a quoted Delta table. The selected key must be non-null and unique for every table row. Generated code checks that invariant with a full-table aggregate before each non-empty save and also rejects null or duplicate keys in the edited rows. No App service-principal retry is used.

Databricks documents primary-key and unique constraints on Delta/Unity Catalog tables as informational and not enforced, so the app cannot treat the selected column or a declared constraint as a database-enforced key. The preflight aggregate and subsequent MERGE are separate statements: a concurrent writer can change key uniqueness between them. The workspace test, DML permission behavior, statement parameter behavior in MERGE, SQL warehouse resource binding, and generated Streamlit execution are unverified. Non-Delta or unreported table formats are displayed read-only. Lakebase table bindings remain preserved but do not use this SQL path. See the [official Databricks constraints documentation](https://docs.databricks.com/aws/en/tables/constraints) and [Delta MERGE documentation](https://docs.databricks.com/aws/en/delta/merge).
