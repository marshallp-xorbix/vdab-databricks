Create-new also inherits the App Space reported for the installed VDAB App through the first-party Apps CLI/SDK `space` field; link-existing requires the same App Space and validates effective scopes when returned. ## Child-app lifecycle

1. Implement explicit `create new` and `link existing` flows in the installed workspace. Validate name, the acting creator/collaborator's management permission, quota, source access, and resource prerequisites before changing remote state. If Databricks App Spaces are used, create-new copies the installed VDAB App's space and link-existing requires the same space. Account for the admin-configured space role, `CAN CREATE APP` permission, allowed scopes, and effective scopes. For an existing app, show the target and current deployment, require confirmation before replacing code, and retain recovery information.
2. Generate a complete child-app source tree in a controlled temporary area; do not rely on runtime filesystem persistence. Select a deployment source supported by the customer's workspace policy (workspace files or Git). Account for admin-enforced Git-only deployment and private repository credentials per child app.
3. Create or update the Databricks App and bind **existing resources in the installed workspace** with the acting user's identity proven by G2. Do not create SQL warehouses, Jobs, Lakebase databases, model endpoints, or Unity Catalog assets. Separate resources granted to the builder from resources granted to each child app. Show required SQL warehouse, UC, Job, Lakebase, secret, and model permissions before deploy. Configure the child app's user authorization so viewer-triggered SQL and Jobs use each viewer's grants where Databricks supports it.
4. Upload/sync source, deploy, poll asynchronous status, link to the App's Databricks runtime logs, and persist version/source/deployment IDs. Handle name collision, retry after partial success, rollback to last successful deployment, and failed resource grants without orphaning an App silently. The current Apps deployment API has no cancel operation; do not substitute stopping compute for cancelling a deployment.
5. Enforce workspace app quota and transparent cost/compute information. Do not promise unlimited child apps; current Databricks limit is 100 apps per workspace.

## Marketplace package and installer journey

1. Produce a self-contained, reproducible, pinned Node package with `app.yaml`, manifest/resource/scopes documentation, license/third-party notices, an SBOM if required by review, and a security review packet. Exclude local `.env`, test data, and secrets. The local `.build/` package and its build/smoke checks are implemented; review acceptance is not.
2. Define first-install prerequisites: Databricks Apps support, Unity Catalog, required user scopes, a customer-owned Lakebase Autoscaling database, optional SQL warehouse/AI endpoint, compute size, egress policy, and administrator grants. Provide a setup validation page that diagnoses each missing permission/resource.
3. Databricks' [current consumer guide](https://docs.databricks.com/aws/en/marketplace/get-started-consumer) says vendors submit third-party Apps for a comprehensive security review before publication. After approval, a consumer installs from the Marketplace Apps category, configures required App resources and scopes, and receives an update notice when new versions are available. Confirm VDAB's provider eligibility and exact vendor submission channel, then test the intended install, upgrade, and rollback in clean workspaces. This documented general flow is not evidence of VDAB approval or an install.
4. Public provider onboarding currently requires applying through the Databricks Data Partner Program; private-exchange-only provider signup is self-service for an account admin. Confirm which provider path accepts VDAB and the terms required for the third-party App. Per D7, VDAB has no in-app license server, license key, or payment check. The consumer guide's App terms step and the data-product guide's external commercial transactions do not establish a paid App purchase or entitlement signal. Do not infer a license from SSO or a purchaser's token.
5. Establish patch distribution, release notes, vulnerability response, and customer support diagnostics. A Marketplace update must not overwrite customer projects or child apps.

## Verification and exit criteria

- Test successful and denied create/link/deploy/redeploy flows with non-admin user roles; test partial failures, quota, and resource policy denial.
- Install and update the builder from the intended Marketplace channel in a separate customer-like workspace; build and run a child app there.
- VDAB provider eligibility, third-party App submission, security review, commercial terms/entitlement, consumer install/update/rollback, and the required release-support process are confirmed and recorded. Any remaining external gate is a release blocker, not assumed complete.
